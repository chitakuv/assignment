### **子阶段 2：审计子系统与热管理（139 - 145）**

##### **2.1：Audit 审计子系统初始化（行 139–140）**

139 [    0.008807] audit: initializing netlink subsys (disabled)  
140 [    0.008870] audit: type=2000 audit(0.008:1): state=initialized audit_enabled=0 res=1

**功能概述**

- Audit 子系统 提供内核级的安全审计通道，通过 Netlink 向用户空间（如 auditd）发送 syscall、SELinux、AppArmor 等审计事件。
- audit_enabled=0 表示编译进内核但默认关闭，只有接收到 audit=1 启动参数或通过 netlink 配置后才会真正开启。

**关键代码与调用链**

```c
/* kernel/audit.c */  
static int __init audit_init(void)  
{  
    /* 如果内核参数 audit=0，就直接跳过后续初始化 */  
    if (audit_initialized == AUDIT_DISABLED)  
        return 0;

/* 创建缓存，用于存放待发送的 audit_buffer */  
    audit_buffer_cache = KMEM_CACHE(audit_buffer, SLAB_PANIC);

/* 初始化多条 skb 队列 */  
    skb_queue_head_init(&audit_queue);  
    skb_queue_head_init(&audit_retry_queue);  
    skb_queue_head_init(&audit_hold_queue);

/* 注册 Netlink 子系统，用于 auditd 进程通信 */  
    audit_netlink_init();   /* 内部调用 netlink_kernel_create()，打印 “audit: initializing netlink subsys” */

/* 标记已初始化，并打印第一条审计消息 */  
    audit_initialized = AUDIT_INITIALIZED;  
    audit_log(...);         /* 则会看到 “type=2000 audit(...) state=initialized” */  
    return 0;  
}  
subsys_initcall(audit_init);
```
- **subsys_initcall(audit_init) ** 
    在 start_kernel() → do_initcalls() 期间执行，早于大部分设备驱动注册。​
- **audit_netlink_init()  **
    内部通过 netlink_kernel_create(&init_net, NETLINK_AUDIT, &cfg) 创建 AF_NETLINK 套接字，并注册回调，以便后续审计事件能通过 Netlink 传递给用户空间。
- **审计状态  **
    第一条审计记录由 audit_log() 生成，格式为 type=2000 ... state=initialized audit_enabled=0，表明框架已就绪但未启用。​

##### **2.2：thermal_sys 热管理子系统初始化（行 141–145）**

141 [    0.008937] thermal_sys: Registered thermal governor 'fair_share'  
142 [    0.008938] thermal_sys: Registered thermal governor 'bang_bang'  
143 [    0.008939] thermal_sys: Registered thermal governor 'step_wise'  
144 [    0.008939] thermal_sys: Registered thermal governor 'user_space'  
145 [    0.008943] thermal_sys: Registered thermal governor 'power_allocator'

**功能概述**

- **Thermal 子系统** 负责根据传感器温度自动调节系统热量输出，绑定多种“governor”策略，用于不同场景：

- **fair_share：**基于各设备“贡献度”分配制冷资源
- **bang_bang：**简单双点阈值控制
- **step_wise：**线性比例调节
- **user_space：**让用户空间程序接管
- **power_allocator：**基于功耗模型动态分配功耗预算

**关键代码与调用链**

```c
/* drivers/thermal/thermal_core.c */  
static int __init thermal_init(void)  
{  
    /* 将各个 governor 结构体注册到框架链表 */  
    thermal_register_governor(&thermal_gov_fair_share);  
    thermal_register_governor(&thermal_gov_bang_bang);  
    thermal_register_governor(&thermal_gov_step_wise);  
    thermal_register_governor(&thermal_gov_user_space);  
    thermal_register_governor(&thermal_gov_power_allocator);  
    pr_info("Registered thermal governor '%s'\n", governor->name);  
    return 0;  
}  
core_initcall(thermal_init);
```

- **core_initcall(thermal_init)  **
    在 start_kernel() → do_initcalls() 阶段中，比大多数驱动初始化略早执行，确保 Governor 在任何 thermal zone 注册前就绪。
- **thermal_register_governor()  **
    将传入的 struct thermal_governor（包含 .name, .bind_to_tz(), .throttle() 回调）加入到全局 thermal_governor_list，并在 /sys/class/thermal/ 下可见对应 governor 名称。
- **Governor 调用**  
    当具体平台或 ACPI 驱动通过 thermal_zone_device_register() 注册传感器后，会默认绑定首个可用 Governor（通常由 DEFAULT_GOVERNOR 或内核配置决定）来实现温度采样与设备限频/降频等动作。

### **子阶段 10.PCI 端点设备枚举（353 - 370 行）**

关键日志  
pci 0000:13:00.0: BAR 0: assigned [mem 0x3ee00000-0x3ee03fff 64bit]  
pci 0000:13:00.0: enabling device (0000 -> 0003)  
pci 0000:13:00.0: PME: Signaling with IRQ 22

**干了什么？**

- 为 PCIe 子设备分配 BAR 地址（内存或 IO 区域）
- 设置 PCIe Bridge window（桥接器资源）
- 分配并连接中断（普通 IRQ / MSI）
- 完成对 PCI 拓扑中每个设备的资源绑定

- 注册 pci_driver 中的 probe 函数（如网卡驱动）

**主要工作**

1. BAR 分配
	对于每个未配置（IORESOURCE_UNSET）的 BAR，内核调用`pci_assign_unassigned_resources(dev);  `
	该函数遍历设备的 BAR 资源，找到空闲的 I/O 或内存地址段，并为其分配地址。​\
2. 启用设备
	调用  pci_enable_device(dev);  
	使能 I/O 和内存访问，唤醒设备（如果之前处于低功耗），并激活 bus-mastering。​
3. 启用 MSI 中断
	如设备支持 MSI，调用  `pci_enable_msi(dev);  `
	在设备上配置 Message Signaled Interrupts，并分配对应的 IRQ 号。
4. 读取并注册中断
	**调用  **
    irq = pci_read_irq(dev);  
	读取从 ACPI/DT 或 MSI 分配到的中断向量，并在内部调用 request_irq() 完成中断注册。
	日志中的 PME: Signaling with IRQ 22 即表示设备的 PME# 事件将通过该 IRQ 线传递。
5. 驱动探测（probe）
	- 枚举完资源并启用设备后，内核在完成所有端点设备的初始化后，会调用  `pci_register_driver(&your_pci_driver);  `
    对于已经匹配的设备，框架调用其 .probe() 回调，让具体驱动（如网卡、存储控制器）接管该设备。

**调用链简图**
```
pci_scan_child_bus(bus_n)  
└─ pci_setup_device(dev)            // 常规 PCI 设备初始化
	├─ pci_assign_unassigned_resources(dev)       
	├─ pci_enable_device(dev)       
	├─ pci_enable_msi(dev)       
	├─ irq = pci_read_irq(dev)  
    └─ (后续由驱动模型) pci_register_driver() → driver->probe(dev)  
pci_setup_bridge(dev)                // PCI 桥设备也走类似流程但会额外设置 window
```

**本阶段意义**  
完成对每个 PCIe 端点（Endpoint）的资源分配、设备启用、中断接入及驱动挂钩，从而让上层设备驱动能够正常访问硬件并处理外设事件。

### 子阶段 11.PCI 总线资源与核心子系统初始化（371 - 790 行）

**主要工作**

**本阶段意义  **
